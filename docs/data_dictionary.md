# Data dictionary

Synthetic classifieds marketplace. Generated by `liquidity/generate.py`, seed 42, 90-day window
starting 2026-01-05. Files land in `data/raw/*.parquet`.

**The platform does not observe sales.** There is no `true_sale` column anywhere in `data/`.
Latent quantities live only in `_truth/ground_truth.json`, which analysis modules are forbidden
to read (`tests/test_no_truth_leak.py`).

## `regions.parquet` — 6 rows

| Column | Type | Meaning |
|---|---|---|
| `region_id` | str | `msk`, `spb`, `ekb`, `nov`, `kzn`, `reg` |
| `region_name` | str | display name |
| `population_tier` | int | 1 = largest, 3 = thin supply (drives zero-result rate) |

## `categories.parquet` — 5 rows

| Column | Type | Meaning |
|---|---|---|
| `category_id` | str | `goods`, `services`, `realty`, `auto`, `jobs` |
| `category_name` | str | Товары / Услуги / Недвижимость / Автомобили / Работа |

## `sellers.parquet`

| Column | Type | Meaning |
|---|---|---|
| `seller_id` | int | surrogate key |
| `seller_type` | str | `private` / `pro` / `business` |
| `region_id` | str | seller's home region; listings inherit it |
| `tenure_days` | int | account age at data start |
| `verified` | int | 0/1 |

## `listings.parquet` — the analysis unit

| Column | Type | Meaning |
|---|---|---|
| `listing_id` | int | surrogate key |
| `object_id` | int | **dedup key.** Equal across duplicate listings of the same item |
| `seller_id` | int | FK |
| `seller_type` | str | denormalised for convenience |
| `category_id` | str | FK |
| `region_id` | str | FK |
| `price_rub` | int | asking price |
| `quality_score` | float | 0..1, latent quality proxy (photo/text/completeness) |
| `relevance_static` | float | 0..1, static part of the rank score |
| `publish_day` | float | days since `data_start` |
| `publish_ts` | str | ISO timestamp |
| `boost_purchased` | int | 0/1 — seller bought paid visibility |
| `boost_start_day` | float | `inf` when not purchased |
| `boost_end_day` | float | `inf` when not purchased |
| `status` | str | `active` / `removed` (as of the end of the data window) |
| `removal_reason` | str \| null | **visible** reason: `sold` / `withdrawn` / `expired` / `violation`. Null when active |
| `removal_day` | float | days since `data_start`; NaN when active |
| `status_ts` | str \| null | ISO timestamp of removal |

`removal_reason == "sold"` is the platform's only claim about a transaction. It is a
**self-report by the seller** and is wrong in both directions. That is the subject of the repo.

## `searches.parquet`

| Column | Type | Meaning |
|---|---|---|
| `search_id` | int | surrogate key |
| `buyer_id` | int | FK |
| `day` / `ts` | float / str | session time |
| `category_id`, `region_id` | str | query context |
| `in_holdout` | int | 1 = promoted slots suppressed for this session (10%) |
| `n_results` | int | impressions actually served |
| `zero_result` | int | 1 = no listing matched (thin supply) |

## `impressions.parquet`

| Column | Type | Meaning |
|---|---|---|
| `impression_id` | int | surrogate key |
| `search_id` | int | FK |
| `listing_id` | int | FK |
| `buyer_id` | int | denormalised |
| `position` | int | 1-based rank within the SERP |
| `is_promoted` | int | 1 = paid slot, 0 = organic |
| `day` / `ts` | float / str | session time |

## `views.parquet`

Impression rows that turned into a card view. Same keys plus `view_id`. View probability is a
steep function of `position` — this is why displacing an organic listing costs it contacts.

## `contacts.parquet` — the demand signal

| Column | Type | Meaning |
|---|---|---|
| `contact_id` | int | surrogate key |
| `listing_id`, `buyer_id` | int | FK |
| `position`, `is_promoted` | int | context at contact time |
| `channel` | str | `call` / `message` |
| `seller_replied` | int | 0/1 |
| `reply_lag_hours` | float | NaN when never replied |
| `day` / `ts` | float / str | contact time |

**Counting rule:** one distinct `(buyer_id, listing_id)` pair = one contact. Summing rows
overcounts: the same buyer can view and contact in several sessions.

## What is deliberately absent

- no `true_sale` — the platform cannot see it
- no `orders` table — there is no on-platform transaction
- no `fraud_flag` on listings — trust & safety is out of scope (see `README.md`)
- no session-level revenue — monetisation is captured only as `boost_purchased`
